### version 2.0.0 (unreleased)

#### Breaking

- `seedReferenceID` is the mount-time seed only. A change to the prop after mount no longer resets the list, and a new `fetchCells` identity no longer resets it either (the latest `fetchCells` is still the one every fetch calls). A host repositions the list with `calls.fetchCradleCells(id)` and clears it with `calls.fetchCradleCells('')`, as before; those are now the only ways to do either after mount, so one host action is one reset. Previously a prop-driven reset queued behind the host's own `fetchCradleCells` and overrode it, which left the list at the prop's row rather than the host's. A list cleared with `fetchCradleCells('')` now stays empty through a resize until the host seeds it again (it used to be re-seeded at the prop), and a list mounted with `seedReferenceID` null and seeded by `fetchCradleCells` is now reconfigured on a resize like any other (it used to be skipped)

#### Changes

- Behaviour change: a gesture across the list's axis now goes through to whatever scrolls behind the list (`overscroll-behavior: auto` on that axis), so a vertical list inside a horizontally scrolling container, or a horizontal list inside a vertically scrolling page, no longer swallows it; the axis the list scrolls along stays contained (`none`) as before. New `operations.crossAxisChaining?: boolean` (default `true`); `false` turns it off for one scroller, which keeps the list scrolling itself on that axis when its cells are wider than its frame and only stops the gesture going on from the list's edge. Consequence: a pull down over a horizontal list now reaches the page, so on a browser with pull-to-refresh it starts one when the page is at its top, unless the host blocks it at the root (`overscroll-behavior-y: none` on `html` / `body`); likewise a sideways swipe over a vertical list can start the browser's back/forward swipe as it does over any other element, unless the host sets `overscroll-behavior-x` at the root. A host that wants neither and cannot touch its root passes `false`
- Behaviour change: a `fetchCells` that rejects, or that resolves with anything other than an array, no longer stops the scroller. The failure goes to `callbacks.error` (`source` is `fetchCells, seed`, `fetchCells, forward` or `fetchCells, backward`; `arguments` holds the `direction`, `referenceID` and `count` the host was called with; `return` holds what came back when it was not an array) and is read as an empty batch, so that pass ends there and the next scroll asks again. Previously the failure escaped as an unhandled promise rejection with the observers left disconnected, and the list never fetched again. An empty array is still the end of the data and reports nothing
- Behaviour change: `calls.fetchCradleCells` now resolves a boolean (it resolved `undefined`): `true` when the cradle was reset, cleared (`''`) or filled as asked, and `false` for a reset that returned early (an invalid `referenceID`, or a call made before the scroller has measured its layout). A reset asked for before layout used to seed nothing and say nothing, and the list then opened on the mount-time seed; it now reports to `callbacks.error` (`source: 'reset'`, the message names the early return), and the `referenceID` is held and seeded from as soon as layout is known, in place of `seedReferenceID`. The promise resolves `false` rather than rejecting, so that a host call written without a `catch` does not become an unhandled rejection. A fill (`fetchCradleCells()` with no `referenceID`) on an empty cradle, after a clear or a seed the host answered with no row, now fetches nothing, resolves `false`, and says so to `callbacks.error` (`source: 'fetchCradleCells'`; the message says there is nothing to fill from); it used to resolve `true` after asking `fetchCells` forward and backward with no `referenceID`. Ruled (Henrik): *"'Recommendation: fetch nothing, report nothing to fill from, and resolve false' agreed"*, *"there should be an error or warning from the scroller to the host for either of these circumstances"*, and *"'Fill on an empty cradle' error = unable to continue"*: an error, since the fill cannot go on. A `remove`, `move`, `replace` or `dispatchEvent` whose target the cradle does not hold still warns, because its purpose is already met; the README's `callbacks` row gives the line (Henrik: *"good refinement"*)
- Behaviour change: a `fetchCells` batch that carries the same `id` twice now loads the first and skips the repeat, which goes to `callbacks.error` (`source` `fetchCells, forward` or `fetchCells, backward`; the message names the duplicate; `arguments` holds the repeated cellPack and `return` the batch after any cellPacks beyond `count` were cut off, which go to `callbacks.failed`). The rest of the batch loads. Previously the repeat went into the cradle as a second cell with the same id: the DOM held two containers for it, React warned of duplicate keys, and every later fetch from that end was refused as a duplicate, so the list stopped filling there with nothing said about the batch. An id the cradle already holds is refused as before (`fetched cellPack is a duplicate`), and that still aborts the batch
- Behaviour change: `spacing` and `cellDimensions` are checked as they are read. A value that is not a finite number of zero or more (`NaN`, `Infinity`, a negative, a string such as `'25px'`) goes to `callbacks.warning` (`source` `spacing` or `cellDimensions`; `property` names the value, such as `cradleMargin[0]` or `minWidth`; `arguments` holds it and `used` the value used instead), and the last good value is used in its place; for `spacing` at mount that is the default. Where nothing can stand in, which is a `cellDimensions` field that has had no good value yet, the report goes to `callbacks.error` instead, with `used` undefined. Ruled (Henrik): *"any internal substitution of inputs needs a warning"*, and *"error = unable to continue"*. The two `cellDimensions` fields the cradle divides by must also be above zero: for a vertical list `minWidth`, and `maxHeight` in a uniform layout or `minHeight` in a variable one; for a horizontal list `minHeight`, and `maxWidth` or `minWidth`. A `0` in either is refused in the same way (the message says the orientation and layout divide by it), and the fields are checked again when `orientation` or `layout` changes. Ruled (Henrik): *"'Recommendation: refuse 0 in each field the current combination divides by.' agreed"*. `0` stays good in `spacing` and in a field the cradle does not divide by. A change whose new values are all rejected leaves the list as it was, with no reset. An absent `spacing` value is still `0` and reports nothing. An absent `cellDimensions` field that the orientation and layout read is now reported as required and held at its last good value, as a bad one is (`callbacks.warning`), or goes to `callbacks.error` when it has had none; a field they never read (`minHeight` in a uniform vertical list, `minWidth` in a uniform horizontal one) may be absent and reports nothing. A list mounted without a field the cradle divides by lays out nothing until it arrives, as before. One that loses it after mount now lays out with the last good value; it used to keep the rows it had while each container laid out afterwards was sized from the missing field (`undefinedpx`). `cellDimensions` has no default, so a bad field before any good one is left out, and a `cellDimensions` that is not an object is reported as required and held at the last good value, or, before there is one, goes to `callbacks.error`, and the list lays out nothing until a good value arrives. Previously each value was used as given: a string was concatenated into the layout arithmetic, `NaN` reached `cellsPerBand` and the cradle was sized from it, a `0` the cradle divides by sized it for more cells or bands than fit (a uniform vertical list's `maxHeight: 0` took it from 8 visible bands to 24, and with no band padding to an infinite count that fetched its whole dataset), an absent field said nothing, and a `cellDimensions` that was not an object threw to the error boundary
- Bug fix: the scroller mounts under `React.StrictMode`. Its own cleanup removed the viewport from the DOM (`viewportRef.current.remove()`), and StrictMode runs every effect's cleanup once at mount, so the second mount watched a detached viewport and never seeded, and the real unmount then threw from React's commit (`Failed to execute 'removeChild' on 'Node'`). React owns that node, and the cleanup is gone. The cleanup that disconnects the observers now also clears the scroller's timers (the resize debounce, the scroll-momentum hold and the restore-scrolling timer) and the flag that says the IntersectionObservers are connected, so nothing of a mount outlives it: fifty mounts and unmounts leave no timer, animation frame or observer behind, and a scroller remounted under StrictMode seeds, fills and unmounts as one mounted once does
- Behaviour change: a `calls` function invoked after the scroller is unmounted does nothing and answers with the empty value of its kind: `insert`, `remove`, `move`, `replace` and `fetchCradleCells` resolve `false`, `getCradleIDList` answers `[]`, `getCradleSpecs` `null`, and every other call `false`. The first such call goes to `callbacks.warning` (`source` is the call's name, the message says the scroller was unmounted and nothing was done, `arguments` holds the call's), or to `console.warn` when the host gives no `warning`; later calls on the same instance are silent. Previously the `calls` object kept the unmounted instance's functions, which ran against its stale state and detached DOM
- Behaviour change: the resize debounce is `SHORT_MOMENTUM_FADE` (200 ms by default) in every state. The code meant to read `STANDARD_SCROLL_MOMENTUM_FADE` (700 ms) once the scroller was set up, and the README said so, but the observer's callback was created once, at setup, and kept reading the setup value, so every host has had 200 ms since 1.x. The ruling keeps what hosts had. `STANDARD_SCROLL_MOMENTUM_FADE` is now the scroll-end debounce and the end-of-data hold's floor only, and the README's Technical section describes each key once
- Bug fix: `spacing` and `cellDimensions` are read into the layout in the commit they arrive in. They were written by passive effects and read by the layout effect of the same commit, so the first layout after a change used the old values and the new ones landed a commit later; both are layout effects now, declared ahead of the one that reads them. Two readings that followed from the same ordering: every mount compared the validated spacing with the raw prop and read itself as a reconfiguration (the first layout is a mount now), and a bad value set at mount was reported twice under `React.StrictMode`, which runs the reporting effect twice (once per instance now)
- Bug fix: an error thrown inside a queued cradle operation (a scroll shift, an overflow trim, `insert`, `remove`, `move`, `replace`, a fill, a reset, a resize) can no longer leave the IntersectionObservers disconnected; the reconnection is in a `finally`. Where the scroller itself discards the operation's promise (the work a scroll starts, and the layout effect) the error is reported to `callbacks.error`, with `source` `evaluateIntersections` or `cradlePotential`, instead of escaping as an unhandled rejection
- Bug fix: a forward trigger crossing with no tail bands in the cradle returned with the observers disconnected; they are now disconnected only after that guard
- Bug fix: a fetch still in flight when the scroller is unmounted or reset no longer writes into a cradle that is gone (the forward and backward fetches re-check after their `await`, as the seed fetch did); an unmount mid-fetch used to throw `Cannot read properties of null (reading 'append')` as an unhandled rejection
- Bug fix: when the seed fetch returns nothing, no `fetchCells('forward', undefined, n)` or `fetchCells('backward', undefined, n)` follows it; the cradle stays empty until the host seeds it
- Bug fix: a trackpad fling into an end of the data put the list back two or three times, because the hold on scrolling was released while the fling's wheel events were still arriving; the hold at an end of the data now lasts until the wheel has been quiet for 300 ms (and never less than `STANDARD_SCROLL_MOMENTUM_FADE`), and a wheel away from that end releases it at once. The wait for quiet also ends once the host's `fetchCradleCells` has reset the list or brought cells to that end. A hold anywhere else in the data, and one that follows a position recovery, is released after `STANDARD_SCROLL_MOMENTUM_FADE` as before
- Bug fix: Safari passes the wheel over a held (`overflow:hidden`) list to a scrollable ancestor in spite of `overscroll-behavior`, so a fling into an end of the data scrolled what is behind the list; a wheel along the list's axis is now cancelled while the list is held, wherever the browser allows it (a wheel mostly across the list, and a pinch zoom, are left alone). The `wheel` listener is non-passive and is attached only for the life of a hold
- Bug fix: a scroll back out of an end of the data, begun while the list was held, moved the ancestor instead of the list in Safari and waited more than a second in Firefox, and in Safari what was left of a fling when any hold let go moved the ancestor too; in every hold the list is now made scrollable again as soon as a wheel has been cancelled, and the cancelled wheel is what holds it. Where the wheel cannot be cancelled (a fling in Chrome and Edge) or none arrives (touch, keyboard, scrollbar) the list stays hidden for the hold, as before. Known limit: a wheel that Safari will not let be cancelled can still go to the ancestor while the list is hidden (WebKit bug 243452); measured in Safari 27, that moved the ancestor in 2 of 72 holds
- Bug fix: in a variable layout a scroll could shift the wrong number of bands and then shift one or more back, or shift back and forth with no scroll input at all. The backward-shift count was measured over the tail band list where the shift takes bands from the head list, and the forward-shift count walked the tail list from its far end where the shift takes bands from its near end; each count now walks the list the shift takes from, from the end it takes from. The backward count also began its span with the lead head band's own height, where the trigger it answers sits at the top of that band, so the span is now the bands beyond it (the lead band always moves). A uniform layout was never affected, because every band is the same size
- Bug fix: the tail-overflow hold records the position every later scroll event is reverted to, and its `scrollLeft` line read `scrollLeftRef.current - viewportRef.current.scrollLeft`, a subtraction with no effect, so the recorded `scrollLeft` was the last scroll event's rather than the viewport's at the hold. It is an assignment, as the `scrollTop` line beside it always was. What it changes is narrow: a scroll made from inside a scroll event on the frame that runs the list into tail overflow is kept rather than put back, across a vertical list pinned sideways, and along a horizontal list only where the fill brings cells, because a scroll past the end of a full cradle, or of the data, is snapped to the content boundary either way
- Bug fix: a resize that changes `cellsPerBand` now keeps the head's leftover cells. When the backward cells did not divide evenly into bands of the new width, the head loop applied its ragged-edge offset to both the start and the count of the slice it re-parented into the outermost head band: with r cells left over and a new width of n it read `slice(2(r − n), 3r − 2n)`, which took cells from the tail end of the list when 3r < 2n (the tail loop then took them back, and the r head cells were left out of the DOM while the list still held them), and read nothing when 3r ≥ 2n (the band was emptied and the r cells were removed from the list and the DOM, then fetched straight back by the fill that follows a resize, so the host saw a `removed` callback for cells that were never over capacity and a backward fetch for cells the head already held). The slice now starts at `max(0, index − (n − 1))` and its count follows from that, so the outermost band holds exactly the cells left over
- Bug fix: each scroller now keeps its own `operations.runway` and `technical` settings (`STANDARD_SCROLL_MOMENTUM_FADE`, `SHORT_MOMENTUM_FADE`). They were held once for the whole module and written by each scroller as it mounted, so with two scrollers on one page the last one mounted decided the runway and the momentum fades for both: `getCradleSpecs()` reported its runway on each, each cradle was sized from it, and a hold lasted for whatever fade the module held when that list first rendered, which could be another scroller's, or one left by a list since unmounted. A change to `operations.runway` on a mounted scroller also went unread, because the settings were written again only when `technical` changed; it now takes effect: a larger runway is filled at once, and a smaller one is trimmed at the next scroll, as a smaller viewport is. A fade is read each time its timer is set. The defaults are unchanged
- Bug fix: a list cleared with `fetchCradleCells('')` now stays empty through a change of `orientation`, `layout`, `cellDimensions` or `spacing`, as it already did through a resize; such a change used to reset the list to the row it was cleared from. The clear drops the axis with the rows, so `getCradleSpecs()` reports `axisReferenceID` as `null` after it (it reported the row the list was cleared from), and the `axisReferenceID` callback fires when the list is next seeded, even at that same row. The clear itself still fires no callback
- Bug fix: a seed the host answers with no row, and a `fetchCradleCells` at a `referenceID` that is not valid, now let go of the row the list was on, as the clear does. Both had already emptied the cradle but kept the axis, so a later change of `orientation`, `layout`, `cellDimensions` or `spacing` reset the list to the row it was on, and it came back unasked. It now stays empty, `getCradleSpecs()` reports `axisReferenceID` as `null`, and the `axisReferenceID` callback fires when the list is next seeded
- Bug fix: a `null` in a `fetchCells` batch is refused as an invalid cellPack, with that site's message (`cellPack must have valid id and component`) and its handling: a forward or backward batch is aborted and reported as before, and a seed is ignored. `typeof null` is `'object'`, so each check read `null.component` and threw: a forward or backward batch was reported as a `TypeError` from `evaluateIntersections`, and a seed rejected the host's `fetchCradleCells` and told the host nothing. A `null` among the cellPacks beyond `count` no longer throws either
- Behaviour change: every error the scroller sends goes through one reporter, which reads `callbacks.error` when it reports and catches a callback that throws (it goes to `console.error`). Twenty-six sites (the cellPack checks, the `insert`, `remove`, `move`, `replace`, `has` and `dispatchEvent` refusals, the seed checks, and the aborted batches) called the callback themselves, from a copy of the callbacks taken when the function was made (for the host's `calls`, at mount), so a host that changed its `callbacks` could be answered by the old ones, and a callback that threw escaped into the operation that was reporting. The payload is unchanged: `source`, `message`, `arguments`, `timestamp`, and `return` on the aborted batches. The `spacing` and `cellDimensions` warnings go through its twin for `callbacks.warning`, which reads and guards the callback in the same way
- Behaviour change: `Infinity` and `-Infinity` are no longer valid referenceIDs (the check reads `Number.isFinite`, where it read `!Number.isNaN`). Each call refuses one as it refuses any invalid id: `fetchCradleCells(Infinity)` reports `must be a valid seed referenceID`, resolves `false` and, with the fix above, drops the axis, and a cellPack whose `id` is infinite is an invalid cellPack
- Bug fix: `calls.insert` at a head position whose outermost band was full put the displaced cells in the wrong bands. The target's band index was read before the new outer band was unshifted onto the head list, which moves every head band's index up by one, so the cells displaced outward were taken from the band beyond the target's: that band was left over-full and the one beyond it empty, which rendered as a gap. With one cell per band every head insert reaches this. The index is now read after the unshift
- Bug fix: `calls.remove` of the only cell in the outermost band of the head or the tail left that band in the cradle, empty, and rendered as a gap: the test for an emptied outer band ran before the cell left it, so it saw the cell and kept the band. The cell now leaves before the band is tested
- Bug fix: `calls.move` of a tail cell to a head position moved the LAST cell of each head band to the FRONT of the band beyond it as the head grew by one, where it is a band's FIRST cell that goes to the END of the band beyond (the order `insert` uses). Cells landed out of order across the head bands and one was dropped from the DOM; with one cell per band the outermost head cell was dropped and its band left empty
- Bug fix: `calls.move` across the axis read the index of a tail band as if the first tail band were full, on both the tail-to-head path (the target's band) and the head-to-tail path (the source's band); the other paths already allowed for a partial first band. A cradle whose first tail band is partial, which is one with no head block, had the band one short
- Bug fix: the IntersectionObservers can no longer be reconnected while a cradle operation is still running. The gate that holds the reconnection read the queue of operations waiting to run and not the one running, so a reconnection timed from the end of one operation fired while the next was in flight, and the observers then reported the cradle mid-change: a shift against a half-filled list, a position recovery, or an overflow trim that undid the fill in progress. The gate now reads both, and the reconnection that follows an `insert`, `remove`, `move`, `replace` or the layout effect's own operation is deferred past the operation's end like every other, so the last operation to finish is the one that reconnects
- Behaviour change: `calls.restoreScrollPositions` runs as a queued cradle operation and resolves a boolean (it ran at once and returned `undefined`): `true` once the viewport has been scrolled to the recorded position and, with `operations.dispatchAttachedEvents`, the `rs3attached` events dispatched; `false` after unmount, with the one-time warning every unmounted call gives. The `rs3restore` event runs the same operation. Previously the restore ran synchronously from wherever it was raised, in the middle of whatever band shift or fill was in flight, so it could scroll the viewport while a shift was moving bands against it, and the shift then finished against the restored position
- Bug fix: the number of bands a scroll shift moves is measured as the shift runs, from the bands and the viewport as they stand then, rather than when the trigger crossing was observed. The count used to be taken at the crossing and carried into the queued shift, so a shift that waited behind another operation (a fill, an `insert`, a shift the other way) ran with a count measured against bands that had since moved: it could move too many, move bands the wrong way after the scroll had turned, or run a second shift for a crossing the first had already answered. A shift that finds nothing to move when its turn comes (the trigger has left the viewport the other way, or that end of the cradle is empty) moves nothing and fills the cradle as before. The walks that measure the count are unchanged (a variable layout's were corrected earlier in this version)
- Behaviour change: the queue of cradle operations says when it has stalled. A task that enqueues another task on the same queue and awaits it never finishes, because the queue runs one task at a time; every fetch runs inside a queued task, so a `fetchCells` that awaits `calls.insert`, `remove`, `move`, `replace`, `fetchCradleCells` or `restoreScrollPositions` before it returns is that shape, and the list stops. Nesting is not supported, and the queue now says so: when an operation has waited 5 s behind one running operation the host hears once per such operation through `callbacks.warning` (`source` is `queue`; the message names the wait and the nested shape; `waitedMs` and `waiting` are given), or `console.warn` without one. A host whose `fetchCells` takes longer than 5 s while another operation waits hears the same warning, since the queue cannot tell the two apart. The scroller has no development build, so the warning is in every build
- Bug fix: scrolling past the end of the data where the last item is longer than the viewport no longer sends the viewer back to that item's start. A viewport past every edge of the cradle was read as a lost position and recovered to the axis. When the cradle is short of its potential at that end the host has said it has no more there, so the overshoot is now the overflow of that block: the host is asked once more, and the viewport is held at the end of the data. The same at the head. The end had been held before by a tail overflow observed while a seeded last row was still laying out, which the reconnection after the DOM task (above) no longer sees
- Bug fix: the IntersectionObservers are reconnected after a cradle operation by a layout effect, once the cradle the operation produced is committed, and no longer by a one-millisecond timer from the operation's end. The timer was a guess at when the DOM had caught up, and when it fired while the next operation was already running it was refused and set again. A reconnect is now a request the component holds: the operation queue answers it when it drains, after the last operation's commit, so an operation's own cradle is what the observers see first (a request made from inside a click handler was at first answered by the requester, before the operation had finished, and then dropped; the queue is now the one writer). The momentum timers (the resize debounce, the hold's quiet release) are unchanged, and the scroll-end wait is the next entry's
- Scrolling mode ends at the browser's `scrollend` event where the browser sends one (Chrome 114, Firefox 109, Safari 26): the axis reset and the scroll-end intersection check come a few milliseconds after the scroll settles, where they came STANDARD_SCROLL_MOMENTUM_FADE (700 ms) after its last scroll event. The end also ticks the mode-end effect, because a browser that sends `scroll` and `scrollend` in one rendering step (an instant scroll) would otherwise enter and end the mode in one commit, which changes no state and runs no effect. That fade timer stays armed on every scroll event as the ceiling, so a browser without `scrollend`, or a `scrollend` that never arrives, ends scrolling mode exactly as before. While the viewport is held still at the start or end of the data, the hold's own pinning scrolls send `scrollend`s that are ignored, and the hold ends as before
